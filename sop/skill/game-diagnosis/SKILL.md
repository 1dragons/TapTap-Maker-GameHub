# 游戏诊断（GamePropel 数据分析 × 游戏设计 × 可视化看板）

在当前游戏项目中使用 **GamePropel CLI**，结合线上数据分析与游戏设计（含源码核对），找出当前最值得验证的具体优化点，并以**单文件离线可视化 HTML 诊断看板**直观呈现。

本技能根路径：`{{SKILL_ROOT}}\`

默认 Admin Host：`https://game-algo-admin.dictapis.cn`（如用户或当前项目显式指定了其他 Host，则以指定为准）。

---

## 红线约束（全程必须遵守）

1. **本阶段严格只读**：
   - **禁止**修改代码或任何仓库文件（安装 CLI、下载 `$gamepropel` Skill，以及输出诊断 JSON 与 HTML 报告时，**必须全部写到项目仓库外部的可写目录**，严禁污染游戏仓库）。
   - **禁止**发布报表、配置、脚本、Strategy 或实验。
   - **禁止**启动 Run、分配流量，或执行任何其他线上变更。
   - 先完整交付分析结果、可视化 HTML 看板和推荐建议，然后**停下来与用户对齐**，由用户选择具体改动方案。
2. **实验发布前的强授权门禁**：
   - 如果后续建议通过实验验证，发布前**必须**单独向用户完整告知以下 9 项信息：
     1. 目标游戏和人群
     2. 假设与指标
     3. 对照组和实验组的精确差异
     4. 参数或脚本
     5. 流量
     6. 周期
     7. 潜在影响
     8. 止损条件
     9. 回滚方案
   - 只有在用户了解上述全部信息并**明确授权**后，才能发布该实验。
   - **方案发生实质变化时，必须重新告知并再次获得授权。**
3. **凭据与密钥安全**：
   - `ga_org_*`、`ga_admin_*`、`ga_setup_*` 仅留在开发机或 CI 中，**严禁**写入客户端代码、日志文件、聊天摘要、诊断 JSON/HTML 报告或公开仓库。

## Phase 1：准备 CLI 与显式加载 `$gamepropel` Skill

1. **安装或更新 `@gamepropel/cli`**：
   - 开始前先安装或更新 `@gamepropel/cli`。
   - 若全局 npm 目录不可写：优先复用已有 CLI，或执行：
     ```bash
     npm install -g --prefix <项目外可写工具目录> @gamepropel/cli@latest
     ```
     并将对应可执行文件目录（`bin` 或 Windows 下的 `<prefix>` 目录）加入当前会话 `PATH`。
2. **安装并显式加载 `$gamepropel` Skill**：
   - Codex / Claude 环境：执行 `gamepropel skill install --agent <codex|claude>`。
   - Maker、Antigravity 或其他 Agent，以及默认目录只读时：执行
     ```bash
     gamepropel skill install --dest <工具可读取的项目外可写目录>/gamepropel --json
     ```
   - **必须显式读取并遵循 `$gamepropel` Skill**：若当前会话未自动加载，直接从命令返回的 `destination` 路径读取 `SKILL.md`。若文件读取工具不可读，通过 shell 分段读取；遇到输出截断时缩小行/字节范围继续读完，**不要要求开发者重启接入任务**。

## Phase 2：确认身份、权限与游戏绑定

1. **检查当前状态**：
   - 执行 `gamepropel whoami --json` 确认当前游戏、环境和权限，优先复用有效的项目绑定或已有组织登录。
   - 优化目录与历史数据分析需要**正式管理权限**，**严禁通过 `bootstrap` 新建游戏来获取历史数据**。
2. **缺失有效登录时的授权流程**：
   - 优先使用 TapTap 浏览器授权：
     ```bash
     gamepropel login --region <cn|global> --json
     ```
   - 在开发者本机执行时可加 `--open`；若为远程 Agent，向开发者展示返回的 `authorizationUrl`，由开发者在自己浏览器完成授权，并在发起命令的**同一 CLI 环境**完成登录。
   - **备选方案（手工密钥）**：
     - 组织管理员：提供 `ga_org_*` 或目标游戏的 `ga_admin_*`
     - 非组织管理员：提供目标游戏的 `ga_admin_*`
     - 二者只需一种；组织管理密钥位于「Admin 控制台 → 组织管理 → 组织管理密钥」。
3. **选择并绑定目标游戏**：
   - 授权后 CLI 会保存组织管理凭据，**授权本身不会自动选游戏**。
   - 执行 `gamepropel game list --json` 查看游戏列表，核对目标游戏后执行 `gamepropel game bind <gameId> --json` 绑定。
   - **严禁任取列表第一项**（无法根据当前项目明确识别时向用户确认）。
   - **已有接入游戏必须复用原 `gameId`，严禁另建替代游戏**。

## Phase 3：只读数据分析与游戏设计诊断

严格按以下 5 项要求推进，全程保持只读：

1. **获取并遵循优化分析文档**：
   - 执行：
     ```bash
     gamepropel docs optimization --host https://game-algo-admin.dictapis.cn --json
     ```
   - 严格按文档中的“数据与游戏设计分析”方法完成分析；若同版本文档已下载，直接本地阅读。
   - 需要专项分析方法时，可自主执行只读命令 `gamepropel optimize list --json` 和 `gamepropel optimize get <task-id> --json` 并阅读相关文档；注意：**读取这些文档仅用于只读分析，不代表执行目录中的任务**。
2. **核对系统机制与代码真相**：
   - 读取系统描述、广告位定义、事件词典与已有报表。
   - 当前项目有源码时，直接核对核心流程、奖励、资源与解锁条件。
   - 明确区分**必经节点、可选节点和分支节点**，**绝不凭事件/字段名称猜测机制**。
3. **核对数据口径后再下钻**：
   - 先核对平台、版本、人群、样本量、留存观察期与 milestone 上报状态，再从整体核心指标下钻到具体体验环节。
   - **口径铁律**：累计到达**不得**写成首日到达；**不得**把上报异常节点或缺失数据当成真实流失。
4. **用机制解释数据并提炼优化点（最多 3 个）**：
   - 用游戏机制解释数据表现，并通过相关报表交叉验证或代码核对来区分不同可能原因。
   - **最多提出 3 个**有充分依据的优化点，宁缺毋滥；**严禁强凑建议，严禁编造预计提升幅度**。
   - 每个优化点必须写清以下 7 个部分：
     - **数据事实**（附带口径、时间范围、版本/样本等上下文）
     - **机制依据**（来自文档、配置或源码的具体机制与路径）
     - **可能原因**（区分核心主因、次因与已核查排除的原因）
     - **具体改动**（可执行、边界清晰的设计或策略调整）
     - **验证办法**（如何检验改动是否有效及对应核心/护栏指标）
     - **成本风险**（开发/配置成本、负向体验或商业化风险）
     - **未确认部分**（当前数据或代码尚无法证实的缺口与需核实项）
5. **按影响范围、证据强度和成本排序**：
   - 明确给出 1–3 个优化点的推荐顺序与排序理由，准备进入 Phase 4 生成可视化 HTML 看板。

## Phase 4：生成可视化 HTML 诊断看板并停下对齐

分析完成后，**必须**将诊断结论、数据口径、路径下钻漏斗与优化建议渲染为自包含单文件交互式 HTML 看板展示给用户：

1. **确定项目外安全归档目录（严禁写入游戏仓库）**：
   - 若 `{{SOP_ROOT}}` 存在：使用 `{{SOP_ROOT}}\diagnosis-reports\<项目名>\`
   - 否则回退到：`<目标项目父目录>\<项目名>-diagnosis-reports\`（若不可写，回退到 `%TEMP%\game-diagnosis-reports\<项目名>\`）
   - 时间戳 `<TS>` 格式：`YYYYMMDD-HHMM`。
2. **组装诊断 JSON 数据（图表优先，拒绝大段文字堆砌）**：
   - 读取 [references/report-schema.md](references/report-schema.md)，将 Phase 3 核查得到的真实数据按**图表驱动**结构写入 `<归档目录>\diagnosis-<TS>.json`：
     - `overview_metrics`：附带 `gauge_pct`（环形仪）或 `sparkline`（微趋势图）与精简 `delta`。
     - `funnels`：用于绘制真实比例梯形漏斗 + 步转化箭头（标注必经/可选/分支/异常节点）。
     - `charts`：至少提炼 **2–3 张最能说明问题的核心大图**（折线留存曲线 `line` / 关卡或广告柱状对比 `bar` / 构成占比环图 `donut`），全部来自真实报表数据。
     - `decision_flow` 与 `experience_flow`：绘制**修改建议决策流程图**（卡点信号 → 根因判断 ◇ → 建议修改动作 → 验证/止损回滚双分支）以及**玩家体验与改造落点流程图**（标出必经主干、可选/分支支路、现状卡点与绿色建议改造落点）。
     - `recommendations`（最多 3 个）：每项除完整 7 要素与可选实验 9 要素草案外，提供精简 `one_liner` 与内嵌 `visual` 图示（`before_after` 改前改后对照或 `compare` 差距柱图），让用户首屏看图秒懂，点击即可展开完整文字证据。
   - **再次确认**：JSON 中不得包含任何 `ga_org_*` / `ga_admin_*` / `ga_setup_*` 密钥，不得编造数据或预计提升。
3. **运行渲染脚本生成单文件 HTML 看板并自动打开**：
   ```powershell
   python "{{SKILL_ROOT}}\scripts\render_diagnosis_report.py" --input "<归档目录>\diagnosis-<TS>.json" --output "<归档目录>\diagnosis-<TS>.html" --open
   ```
   - 看板离线自包含（零外部 CDN 依赖），采用**护眼浅色图表优先布局**：首屏即见核心 KPI 仪表、真梯形漏斗、留存/关卡/广告可视化大图与优化优先级雷达对比；长段 7 要素明细默认收纳在折叠抽屉中按需展开，不造成阅读负担。
4. **交付结果并停下对齐**：
   - 在聊天回复中提供可点击的 HTML 报告 `file://` 链接，同时给出精炼的文字版核心摘要与推荐排序。
   - 告知用户可在已打开的 HTML 看板中浏览详情并直接勾选意向方案，然后**立即停止等待用户选择具体改动方案**；未获明确指令和授权前，不修改代码、不执行任何线上变更或实验发布。
