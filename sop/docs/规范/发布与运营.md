# 发布与版本运营规范

## 1. 发布前强制前置条件

任何一次构建与上传必须依次满足三道硬条件，缺一不可：
1. **通过全量 QA 闭环**：已执行 `taptap-maker-qa`，静态审计与官方 Lua 校验 0 阻断错误、生产 LSP 0 警告、调试/作弊/诊断开关全部关闭、老存档直升兼容性结论明确；
2. **版本号三处一致**：脚本内版本常量、Maker 工程配置版本、当前最新发版 Git 提交保持一致（可在 GameHub 一眼核验无红色版本冲突）；
3. **获得用户明确构建上传授权**：发布候选确认不等于上传授权，工具提示“需要构建”也不构成授权。

## 2. 新版本运营资料准备（衔接 `mini-game-version-ops`）

发布正式版或中大更新版本时，调用 **`mini-game-version-ops`** 按运营后台表单规范一次产齐可复制资料与素材：
- **严格核实字数与真实性**：按后台顺序交付版本名、卖点、1–3 个合规标签、版本介绍与 1–5 条真实更新重点；所有限长字段按 Unicode 字符数核对，不虚构未上线玩法、不夸大宣传。
- **双规格主视觉素材**：交付与当前游戏真实画风一致的 **16:9 新版本头图** 与 **2.5:1 搜索品牌专区图**（独立构图适配，严禁简单拉伸），主视觉和图标保证小尺寸下清晰可辨。
- **更新公告草稿**：可使用 **GameHub** 的「从 Git 自动生成本版更新日志」功能，过滤零碎云端同步记录，一键整理玩家向更新公告。
- **授权与合规**：字体、音乐、图标与第三方素材授权记录随项目保留，隐私与 SDK 说明如实对应实际接入能力。

## 3. 构建、上传与 GameHub 打卡

1. 获得用户明确授权后，按 `maker://status` 提供的当前构建上传工作流执行构建与上传。
2. 严格区分并分别报告四个独立状态：**本地校验通过 / 远端构建成功 / 已上传后台 / 平台审核上架**；遇到异常先区分代码错误、资源问题、环境绑定与平台波动，状态不明先查询结果，严禁无依据重复提交。
3. 上传完成后在 **GameHub** 对应项目卡片执行 **「打卡：已构建 / 已上传」**，确保工作台三段雷达与发布健康度保持准确。
4. 如发版后发现严重事故需回退，必须先评估老存档版本兼容，**严禁通过清空玩家存档实现回退**。

## 4. 上线后观察与双驱迭代

版本发布后，转入 [数据与玩家双驱迭代](../流程/上线与迭代.md)：
- 用 `game-diagnosis` 跟踪 GamePropel 留存、漏斗与广告表现；
- 用 **GameHub TapTap 评价 & 论坛雷达** 增量拉取新版本玩家反馈，第一时间捕捉 P0 机型闪退、卡死或广告口碑波动。
