# 数据与玩家双驱迭代

游戏上线公测或正式版后，迭代不再靠拍脑袋加系统，而是依托 **「客观数据漏斗（GamePropel）× 真实玩家原声（GameHub TapTap 雷达）」** 双引擎定位问题，小步快跑、每次只打最值钱的 1~3 个点。

## 1. 上线前必须埋好的精简核心埋点

避免上线后“盲飞”，也不要为了埋点堆几十个无人看的垃圾事件。首版上线前至少确保以下两类核心信号干净准确：
- **核心成长里程碑（Milestone）**：启动成功 → 完成首局/序章 → 关键解锁节点（第 1/2/3 次扩建、解锁核心道具/区域、核心循环进入中后期）。
- **广告与商业化漏斗**：每个主要广告位的入口曝光 → 点击请求 → 播放完成 → 奖励到账（严格区分必经节点与可选节点）。

## 2. 双源诊断工作流

### 源头 A：客观数据诊断（`game-diagnosis` + GamePropel CLI）
当版本积累足够样本后，调用 **`game-diagnosis`** 执行只读深度诊断：
- **先核口径再下钻**：核对平台、版本号、样本量、留存观察期与上报异常，严禁把累计到达当成首日到达，也不把漏报节点当真实流失。
- **按环节拆解问题**：

| 环节 | 观察核心 | 优先排查方向 |
| :--- | :--- | :--- |
| 曝光 / 点击 | 商店分发与点击转化 | 图标小尺寸辨识度、标题卖点、16:9/2.5:1 头图与真实截图是否匹配 |
| 启动 / 首局 | 进游戏成功率与首轮完成率 | 包体加载、机型兼容、首分钟引导是否过长或卡死、触控/视角是否劝退 |
| 留存 | 次留 / 多日留存 | 存档丢失、目标断层、中后期重复枯燥、卡顿发烫 |
| 广告 / 变现 | 入口触达、请求、完播、人均观看与收入 | 入口曝光位置（主 HUD vs 藏二级页）、奖励是否解痛点、SDK 回调与广告填充 |

- **输出物**：单文件交互式 HTML 诊断看板（输出到项目外安全目录），最多提炼 **3 个**有充分数据+代码依据的优化点，包含 7 要素与排序理由。

### 源头 B：真实玩家原声雷达（`GameHub` TapTap 评价 & 论坛雷达）
数据告诉你「玩家在哪走」，评价和论坛告诉你「玩家为什么骂 / 想要什么」：
- 在 **GameHub** 项目详情页使用 **「首次全量抓取 → 后续增量拉取新反馈」**，自动拉回最新玩家评价（含星级、机型、游玩时长）与论坛帖子。
- 借助本地六维痛点聚合（闪退/卡死、广告/激励、存档/丢档、数值/难度、操作/UI、建议/好评）与可选内置 AI 总结（推荐「轻度」或「极速」档位），重点盯防：
  - **P0 阻断类**：特定机型闪退、卡死、丢档、看广告没发奖、返回静音——**最高优热修**；
  - **P1 口碑槽点**：广告频率过高引爆 1★ 差评、触控误触、平板/长屏遮挡、数值卡关——**排入近期小版本**；
  - **P2 玩家许愿 & 好评亮点**：高频呼吁的便利功能（如删档/多存档、新区域/新员工），同时守住玩家夸得最多的核心乐趣不被改坏。
- 将筛选确认后的问题一键 **「转待办」** 写入当前项目，直接进入下一轮制作。

## 3. 迭代执行纪律

1. **每次聚焦 1~3 个核心改动**：避免一次把数值、广告、大玩法全改乱导致无法归因。
2. **明确假设与观察窗口**：记录触发证据、改动内容、预期观察指标与止损回滚条件；若涉及线上 A/B 实验发布，必须经用户完整确认 9 项实验告知要素后方可授权执行。
3. **老存档绝对优先**：任何迭代严禁以清空玩家存档换取开发便利，必须通过 `taptap-maker-qa` 老档直升检查。
4. **发版闭环**：改完 → `taptap-maker-qa` 全量体检 → `mini-game-version-ops` 更新版本文案与头图（大/中版本）→ 获得用户授权后构建上传 → 在 GameHub 打卡构建/上传并生成更新公告。
