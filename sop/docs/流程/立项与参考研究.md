# 立项与参考研究

## 从想法到可检验的问题

用户说“做早餐店经营”，Codex 不能直接扩成装饰、员工、任务、签到和排行榜。先明确：玩家扮演谁；一次有意思的行为是什么；订单压力来自哪里；短局结束留下什么期待；手机上如何操作。

用一句话写假设，例如：玩家需要在有限灶位和订单期限间安排制作，连续合理安排会获得可感知的效率提升。原型要检验安排是否有选择，而不是仅检查钱是否增加。

## 研究步骤

1. 找至少一个直接同类案例，观察首屏、首分钟和一次完整循环。另找一个表现参考，避免只参考相同产品。
2. 看得到的记录事实：按钮、操作次序、反馈与节奏；看不到的标记推测，不编造留存和收入。
3. 在 GitHub 找成熟实现时，先读项目说明、版本、许可、演示与引擎要求。星标只辅助筛选。
4. 每个参考只选择具体借鉴点，说明为何适合本项目、改动什么、不能直接移植什么。
5. 形成项目差异：玩家能实际感受到的行为或表现，不用“内容丰富、画面精美”代替。

## 参考记录要求

来源链接、访问日期、固定版本或截图出处、观察范围、借鉴机制、差异、实现成本、资源授权分别填写。代码许可不等于演示图、字体和音频许可。研究下载不代表可以放进正式游戏。

比较时使用相近条件：相同设备方向、类似屏幕大小、相似玩法时段。只比较首页截图不能证明整段体验更好。

## 立项交付与否决

交付 [项目设计书](../模板/项目设计书.md) 的立项部分、[参考分析](../模板/参考分析.md)、原型验证目标与范围上限。暂不展开全部数值和页面。

若核心体验只能靠大量未完成内容、操作不适合触屏、成本显著超出独立开发能力，先缩小范围。若两次有依据的原型调整仍无法说明核心乐趣，向用户展示观察和替代方向，不自动无限扩张。

## 案例研究原则

拆解同类或跨题材作品时，应同时比较作品表达、玩法循环、玩家批评与公开反馈，并明确商店页观察不能替代实机体验。按新项目题材选择参考案例，不把单一作品的模板生搬硬套给所有游戏。
