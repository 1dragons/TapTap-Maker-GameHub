# UI 视觉基线与实现（分级出图工作流）

本流程结合多款 2D / 3D 线上小游戏实战经验，摒弃早期“每个小弹窗都必须先逐页画 AI 整页设计稿”的重负担做法，改为 **「核心基线定调 + 常规弹窗按 Token 直出 + 实机截图/录屏验收」** 的高效率成熟模式。

## 1. 页面分级策略（何时出图、何时直出）

| 页面类型 | 典型示例 | 制作方式 |
| :--- | :--- | :--- |
| **A 类：定调基线页**（必须先定视觉基准） | 主菜单/开屏、核心局内 HUD、核心 2D/3D 主场景平面布局图、最具代表性的 1 张核心卡片/弹窗 | 先通过参考拆解或 AI 视觉基线图确定整体构图、主辅色、字体层级、圆角/描边/阴影与空间动线，经用户确认后提取为项目 **Design Token**。 |
| **B 类：常规功能弹窗与列表**（按 Token 直出） | 设置页、多槽位存档页、商店/升级列表、订单/任务板、排行榜、确认/异常弹窗、结算页 | **不再强制逐页先出整页设计图**。先写简明 [单界面设计表](../模板/单界面设计表.md)（目的、数据、状态、动作），直接复用项目已冻结的 Design Token 与通用组件实现。 |
| **C 类：局部微调与热修**（原地修改） | 调整按钮位置、避让安全区、修文字换行、新增单个角标或胶囊入口 | 严禁推翻重做设计稿；在现有布局与组件上做最小必要改动，直接以本地预览 + 多比例截屏复核。 |

## 2. 定调基线与提取 Design Token

1. **视觉基线要求**：
   - A 类基线图需清晰表达构图、背景氛围、主辅色、按钮权重、卡片层次与信息顺序；图像必须干净无噪点、无随机纹理。
   - **3D 场景类项目**：优先产出**平面功能分区图 / 动线草图**（明确出生点、交互区、视线朝向、扩张区域边界），确认动线无冲突后再搭建白模与精模。
   - 如基线图由 AI 生成，中文文字仅用于示意排版；正式实现中的全部中文、动态数字与按钮标签必须使用真实字体与引擎 UI 组件。
2. **冻结项目 Design Token**：
   从确认的视觉基准中固化一份轻量参数记录（写入 `.sop/设计决定.md` 或项目主题配置 Lua 表）：
   - 色板：主背景、浮层卡片底色、主强调色、次级按钮色、成功/警告/危险状态色、主/次/弱三级文字色；
   - 排版：主字体、字号阶梯（标题 / 正文 / 数值 / 角标）、描边或投影规则；
   - 组件规格：圆角层级、边距基准、主次按钮最小触控尺寸、弹窗遮罩与关闭按钮统一位置。

## 3. 组件化实现与多比例实机验收

1. **按 Maker 官方 UI 工作流实现**：
   - 涉及 `UI.json`、切图或图集更新时，先遵循 `maker://status` 返回的当前 UI 工作流文档；保留既有节点层级与资源引用，不因为改一个控件破坏整个界面树。
   - 优先复用公共组件（统一弹窗框、通用货币顶栏、标准确认按钮、通用 Toast 飘字），杜绝每个页面各写一套硬编码色值与字号。
2. **全比例安全区强制核对**（详见 [界面与交互规范](../规范/界面与交互.md)）：
   - 同时核对 **4:3 平板（iPad）/ 16:9 标准屏 / 20:9 细长屏** 三类比例；
   - 重点检查：右上角平台悬浮胶囊避让、顶部横幅与加钱飘字防重叠、指引条与主操作区不遮挡、底部系统手势区留白。
3. **高效验收产物**：
   - A 类基线页：展示实机截图（必要时附基线对照与多比例截屏）；
   - 3D 场景/大版本更新：推荐输出 **场景审阅 HTML / 短实机录屏** 供用户直观审阅；
   - B/C 类常规页：以本地预览实拍检查全部关键状态（空状态、长文本、大数字、资源不足、连点、返回恢复）。
